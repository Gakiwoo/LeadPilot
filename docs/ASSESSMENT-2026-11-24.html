5. 本次实锤复核：三处「诚实性」破口

5.1 P1 · <context> 来源 URL 未清洗 → PII 终检双向破口（B5 联调回归）

server/protocol.mjs:289-292 把 input.sources[i].url 原样拼进 <context>，只有正文 sourceTexts 过了 sanitizeContext()；gateway.mjs:520 / batch.mjs:512 传入的是原始 sources。本次实跑：

url=https://x.example/about?e=alice@corp.com        context-has-literal-url=true  pii-ok=false  hits=[0]
url=https://x.example/about?e=alice%40corp.com       context-has-literal-url=true  pii-ok=true   hits=[]
url=https://user:pass@x.example/about                context-has-literal-url=true  pii-ok=false  hits=[0]

即：合法 URL 带 @ 会被电话/邮箱正则误判 → 整次请求被 E6004 拦下（可用性回归）；把 @ 编码成 %40 则绕过终检，原文邮箱随 prompt 外发给 provider（违反「官网原文 / 客户邮箱不进 provider」的数据最小化红线）。修复：URL 先过白名单清洗（仅保留 scheme + host + path，剥 query / userinfo），终检对 URL 做 decode 后再匹配，并补 3 个行为级反例。

5.2 P1 · check:tracked 与历史 .gitignore 同款假保证

SKIP_DIRS = new Set(['node_modules','dist','data','coverage','.workbuddy'])   // 按 basename 匹配任意层级
git ls-files src/data -> 2 files: src/data/demo-data.ts, src/data/repository.ts
node scripts/check-clean-checkout.mjs -> 「干净检出校验通过：65 个源码/配置全部纳入版本控制，90 个 tracked 文件无缺失」
git ls-files src server shared scripts | grep -E '\.(ts|tsx|mjs|json|sh|yml|css|html)$' | wc -l -> 67

SKIP_DIRS.has(name) 命中任意层级的 data，把 src/data/ 排除在 walk 之外；根级 8 个配置（package.json / vite.config.ts / ci.yml …）也不在对账范围。如果这 2 个文件哪天未被 git 跟踪，脚本仍会报「全部纳入」，CI 绿而干净检出缺模块——正是 ADR-008 教训的重演。修复：按仓库相对路径锚定（仅根 /data/），根级 tracked 文件纳入全量对账，补「故意漏跟踪一个源码必须报红」的反例。

5.3 P1 · pinnedFetch 没有响应字节上限

server/fetch.mjs:355-388 的生产默认出站用 res.on('data', c => chunks.push(c)) 全量收集再 Buffer.concat，maxBytes=524288 只在下游 readLimited 截断，超限时仍 ok:true, truncated:true——契约里「响应过大 E4012」分支从未实现。独立实测 700000 字节响应被完整读入。修复：data 回调累加字节，超限 req.destroy() 并 reject；fetchOne 对 truncated 返回 E4012。
