# LeadPilot PRD v1.1 · 产品评审与本次交付范围

> 评审视角：高级产品经理 + 高级工程师 · 评审日期 2026-11-06 · 对象：资料库《PRD-LeadPilot-B2B外贸客户开发工作台-v1.1》

## 结论先行

PRD v1.1 是一份**架构判断正确、工程纪律清楚**的文档，尤其是「模型不打分、模型不生产事实、分数必须可复现」「缺失维度不补零」「退订红线写进代码」三条，直接避开了 B2B 数据产品最常见的死法。可以进入评审。

但它**不能按 10 周 MVP 直接开工**：有 4 项不在研发控制范围内的硬依赖（Google OAuth 验证、CASA 评估、数据源采购、385 家人工标注集），其中标注集的人力在排期表里根本没有出现。

因此本次交付定位为 **M1/M2 客户端可运行基线**：把不依赖外部条件、且最能验证产品假设的部分（五维可解释评分 + 12 态状态机 + 合规红线 + 完整主链路 UI）做成真实可运行、可测试的代码；采集 / 模型 / Gmail 走可插拔适配器与**明确标注**的演示数据。这样第 1 周就能拿去给种子用户看「评分到底敢不敢信」，而不是等到第 10 周才发现产品假设不成立。

## 一、PRD 做对的三件事

| # | 判断 | 为什么对 |
|---|---|---|
| 1 | 模型只做「理解、判定、解释」，检索管道负责事实，代码负责算数 | 用 PersonQA / WebLists / GTM Bench 三组证据证伪了「全交给大模型」。同一客户两次调用差 8–15 分的产品，业务员用一次就再也不信 |
| 2 | 「无记录 ≠ 没进口」，海关数据不可得时做权重转移 | 德国、日本、中东是外贸主战场。给 0 分会让这些市场名单全军覆没——这是同类工具的死因 |
| 3 | 数据最小化优先于写合规文件（11.4.1） | 判断「分销商还是零售商」根本不需要邮箱和联系人姓名。从协议层剔除，合规面和 token 成本同时下降，是最高 ROI 的工程决策 |

## 二、三个需要修正的口径问题（PM 判断）

| # | 问题 | 建议 |
|---|---|---|
| 1 | **PRW 北极星单位矛盾**：1.5 节写「PRW ≥ 5%」，但定义是「单用户每周收到的正向回复数」；12.2 又写「≥ 1.5」 | 统一为 **PRW ≥ 1.5 条/周/人**，5% 是回复率，不是北极星。指标口径不一致会让周会报表对不上 |
| 2 | **验收口径自相矛盾**：9.5 明确批评「抽样 10 家看效果没有统计意义」，但 AC-04 用「人工抽检 50 家 · 客户类型准确率 ≥ 80%」，而 9.5 门槛是 Cohen's Kappa ≥ 0.65 | AC-04 改为在 385 家基准集上分层抽样评估，与 9.5 共用口径；并补充**多标签判定规则**——一家公司同时是 importer + distributor 时，命中其一算对还是全中才算对，不定义就无法验收 |
| 3 | **AC-16 离线能力在 MVP 不自洽**：MVP 只建草稿、不发送，本地「待发队列」没有可同步的目标 | MVP 保留「断网可看已缓存详情 + 可编辑开发信存本地」；「待发队列 / 联网自动同步」移到 V1 与 gmail.send 一起验收 |

## 三、10 周排期的真风险（按关键路径排序）

| 风险 | PRD 里的位置 | 我的判断 |
|---|---|---|
| **385 家基准集标注是人力关键路径，但排期表里没有这两个人** | 13 章排期风险④、9.5.3 | 2 名外贸背景标注员 × 2–3 周 + 第三人裁决，且 PRD 明确「不能让研发兼任」。这不是「加个任务」，是**要招/借两个人**。M0 第 1 周不启动，M2 的「首次基准集回归」必然跳票 |
| Google sensitive scope 验证 2–6 周 | R1 | M0 启动是对的，但要准备「验证未过」的降级路径：Apps Script / SMTP 体验差，MVP 至少要保证「草稿能力」不依赖 Google 审核结论 |
| 数据源采购 2–4 周 + 年度锁价 | R2 | 建议 Q1 先采 3 国，同时把 `DataSourceAdapter` 的降级链做成可配置，避免某家断供时改代码 |
| 邮箱验证器 IP 信誉需养 2–3 周 | 13 章风险③ | 自建 MX + SMTP 省 90% 成本，但新 IP 直接探测会被大面积拒绝。这是**最容易被漏掉的启动项**，M0 就要开始养 |

**排期建议**：把 M0 从「1 周」拆成「第 1 周启动 + 全程并行」——标注、OAuth 申请、数据源合同、IP 预热四条外部链路并行跑，研发不等它们；M1/M2 用 Mock 适配器先把评分与主链路做扎实。这正是本次交付的做法。

## 五、成本与定价复核（9.4）

| 方案 | 单任务成本（L2/200） | ¥199 套餐含 7.5 任务 | 毛利率 | 结论 |
|---|---|---|---|---|
| A 全 DeepSeek 谷时 | ≈ ¥4.9 | 成本 ¥37 | 81% | 可做，但判断质量全压 Flash 档 |
| **B 三级路由** | **≈ ¥9.9** | **成本 ¥74** | **63%** | **目标区间** |
| C 全 GPT-5 | ≈ ¥80 | 成本 ¥600 | −201% | 订阅制不可行 |

**补充意见**：9.4 只算了 token + 搜索费，漏了基础设施固定成本——Playwright 集群、代理池、页面快照对象存储、SMTP 验证 IP 信誉养护、EV 代码签名（$300–600/年）。这些不随任务线性变化，但会吃掉低活跃用户的毛利。建议单列一张「固定成本表」再定价。同理 11.4 说「成本主要是工程纪律，不是钱」偏乐观：DPA 签署、ZDR 通道溢价、V2 本地模型部署都是真金白银，且是企业客户的采购前置条件。

## 七、Go / No-Go 判据

进入 M1 全量开发前，M0 必须同时满足：

1. 至少 2 家数据源合同签订或可用沙箱 Key；
2. Google OAuth 验证申请已提交（不要求通过）；
3. 385 家基准集标注启动，**标注员已到位且不是研发兼任**；
4. EV 代码签名证书采购下单；
5. 用本次交付的基线跑一轮 5–10 名种子用户访谈，确认「评分卡证据链是否被点开」——如果证据链展开率极低，说明产品价值锚点没成立，继续堆功能没有意义。

> 北极星之外的那句实话：这个产品最大的风险不是竞品，是**用户敢不敢按这个分数去发信**。所以第一优先级永远是评分可信度，不是数据量。

> **v0.7.0 修订注（口径，不是撤判据）**：以上五条**原文保留、一条未撤**。v0.7.0 用户拍板「定位仍是自动获客、目标用户是批量 SDR」，因此前四条外部依赖从「阻塞研发」重分类为**「发布门禁」**：内测阶段可以先跑第 5 条种子用户访谈并拿真实反馈，但**不得正式发布、不得对外宣称准确率、不得自动发送**。判据本身仍是正式发布的硬条件。详见第十三节。

|---|---|---|---|

## 九、v0.3.0 进展修订（工程化收口，保留上文判断）

这一轮没有新增任何 PRD 功能，做的是**把已有能力变成「敢交给别人跑」的工程基线**。对 PM 而言意义只有一句：从「演示工程」变成「可协作、可复现、可不骗自己」的仓库，但**第七节 Go / No-Go 四条外部判据仍然一条都没解除**。

| 变化 | v0.2.0 | v0.3.0 | PM 视角 |
|---|---|---|---|
| AC-03 杀进程续跑 | ⚠️ 游标只在内存，重启即丢 | ✅ 单实例闭环：SQLite/JSON 落任务、缓存、审计，重启降为 `paused` 并保留点数 | 这是唯一一项**验收标准**，优先级高于任何新功能 |
| 模型可复现 | 协议里写了要锁快照，代码未强制 | ✅ 未锁具体版本返回 `E6008`，`-latest` 判非法 | 直接保护 385 家基准集与 30 天缓存的有效性；宁可降级也不猜版本号 |
| 服务端暴露面 | 仅本机、无鉴权 | ✅ Bearer / CORS 白名单 / 限流 / 启动前置拒绝公网裸奔 | 减少「为了演示方便临时开 0.0.0.0」造成的事故 |
| 协作与回归 | 本地目录，非 git 仓库 | ✅ `Gakiwoo/LeadPilot` + CI（typecheck/test/build/smoke 全链路） | 终于可以多人并行、每次 push 有门禁 |
| 诚实度 | health 报网关状态 | ✅ health 如实暴露 `persistence.mode / durable / recoveredTasks`；`memory` 不会被说成已持久化 | 与「E6005 不是成功」同一条纪律：不把「没有」包装成「有」 |

**必须写进产品口径的三句话**：

1. **AC-03 的 ✅ 带限定词「单实例」**。多实例部署仍需共享库 + 任务租约，对外宣传不能写成「断点续跑已完整支持」。
2. **模型快照锁定意味着真实调用门槛变高了**。只配 Key 会看到 `E6008`，这不是 bug，是刻意设计；设置页必须把「已配 Key」与「已锁快照」分成两列，否则用户会以为产品坏了。
3. **工程风险下降 ≠ 商业风险下降**。数据源采购、OAuth 验证、CASA、385 家人工标注集、EV 签名依旧是排期关键路径；这一轮没有让任何一条提前一天。

**仍不建议开工 10 周 MVP**，理由与第一节完全相同。下一笔研发预算应优先砸在「385 家标注集 + 数据源沙箱」，而不是继续给这个基线加功能。

## 十、v0.4.0 进展修订（补事实链，不补功能）

这一轮做的是**把「分数从哪来」这条链往上补了一节**，而不是加功能。对 PM 而言，它影响的是第一节说的那个真问题——「用户敢不敢按这个分数去发信」。

| 变化 | v0.3.0 | v0.4.0 | PM 视角 |
|---|---|---|---|
| 规则分的输入 | 演示数据里直接给 `RuleFeatures` | ✅ T0 规则抽取：从调用方原文抽可核验事实，逐字引用、未命中 `no_signal` 不补零 | 评分链最底层不再依赖「手填的数字」。但**仍需要调用方提供原文**，当前无数据源，所以还没形成端到端真实链路 |
| 开发信个性化锚点 | 模板自己拼一句 | ✅ 传 `sources` 时锚点来自 T0 可核验引用，返回 `anchorSource`；降级路径也如实上报 | F6-1「可核验锚点」从口号变成可验证字段，给 30 封真实开发信人工复核提供了检查点 |
| 6 类数据源 | 编排器硬编码源名字符串 | ✅ 注册表契约 + 逐源 health，`0/6 已接入` 如实上报；**有实现也 `blocked` 暂停** | 这条「不放行」是产品决策，不是技术保守：一旦半接入产出看起来像真公司的名单，可信度资产当场归零 |
| 回归保障 | CI 跑 typecheck/test/build/smoke | ✅ 加干净检出检查 + 真实杀进程重启 AC-03 | 每次 push 都在验证「别人 clone 下来能不能跑、杀进程会不会丢钱」这两件最基础的信任 |

**必须继续写进产品口径**：

1. **T0 是规则层，不是模型能力**。对外不能说「AI 自动抽取企业事实」；它是确定性词表匹配 + 逐字引用，词表还需 385 家基准集校准后才冻结。
2. **`0/6 已接入` 必须常驻可见**。数据源没接就是没接，界面逐源标「未接入」比给一个漂亮的「采集中」动画重要得多。
3. **`blocked` 不是 bug**。有人注入了数据源实现，任务却暂停，这是刻意的——真实写入要与客户端写入契约、域名去重、原文抓取一起评审。
4. **工程风险继续下降，商业风险纹丝不动**。第七节四条 Go 判据（385 家标注员到位、OAuth 验证申请、数据源合同、EV 签名）一条未解除；Tauri/DPAPI/CASA 也没动。

**结论不变**：下一笔钱和人力应放在「385 家标注集 + 数据源沙箱」。这一轮让基线更值得被拿去见种子用户，但没有让用户多拿到一家真实客户。

| 点数 | 任务结束时赋一个 `pointsUsed`，前端另有本地计数器 | ✅ 服务端账本：创建预扣 / 收尾按比例结算 / 未启动全额释放，幂等、事务化、跨进程不重复扣 | 用户最恨的不是「扣多了」，是「说扣了却没扣、说没扣却扣了」。先把范围写窄、边界写死 |
| 规则与模型的关系 | T0 只服务写信锚点，judge 仍吃手填 facts | ✅ 规则事实进 judge Prompt，冲突由代码保守取规则值、置信度归零并标待复议 | 与 6.7.4「冲突不平均」同一条纪律，避免模型把自己的结论解释成「与规则一致」 |
| 385 家标注集 | 只有 `NOT_LABELED` 一句话 | ✅ 完整导入契约 + 校验器 + 反例夹具 + CI 自检 | 契约先落地，标注员一到位就能开工；同时堵死「生成一批假标注让 CI 变绿」这条路 |

| 前端服务层 | 组件 / store 直连三个具体实现 | ✅ `adapters.ts` 唯一入口 + CI 静态扫描 | 下一次接真实数据源时，改动面收敛到一处 |

**必须写进产品口径的五句话**：

1. **账本范围只覆盖云端任务**。`gateway` 的 `judge` / `write_email` 审计里的 `points` 是 token 折算估值，**不是已扣点**；成功响应带 `billing.charged=false`，`/health.billing.auditOnlyConsumers` 明列。销售材料不得写「全链路精确计费」。
2. **前端本地 `pointsBalance` 与服务端账本不是同一本账**。前者是演示运行器的计数器；对外演示时必须说明，避免被问到「为什么界面点数和服务端不一样」。
3. **T0 事实链已接线，但演示数据不敢用**。前端 `sourceTexts` 没有真实 URL / 抓取时间，绝不拿来伪造 `sources`；设置页如实显示「需调用方提供可核验来源」。
4. **导入校验通过 ≠ 评测通过**。`releaseEligible` 恒 `false`，无标注时 `/v1/eval/run` 仍返回 `NO_DATA`。任何人拿一份格式合法的空壳数据说「评测过了」，都应对照这条反驳。
5. **工程正确性 ≠ 产品可发布**。`npm run gate` 自检全绿但明确打印 `releaseBlocked=true`；自检通过只证明「边界没被伪造」，不证明「可以卖」。

**Go / No-Go 四条判据（第七节）状态：全部未解除。** 385 家标注员到位、OAuth 验证申请、数据源合同、EV 签名仍是排期关键路径。本轮唯一改变的是：当这些外部条件到位时，代码侧不再需要返工就能接住它们。

**结论仍然不变**：下一笔钱和人力应放在「385 家标注集 + 数据源沙箱」。连续三轮工程加固已经把「基线里还藏着假东西」这个风险压得很低，再往前堆工程能力的边际收益明显低于去拿一家真实数据源和一批真实标注。

## 十三、v0.7.0 定位拍板与依赖重分类（保留第七节全部判据）

**用户拍板**：产品定位仍是**「自动获客」**，目标用户是**批量 SDR**。上一轮评估的「简易替代方案」中，把定位降成「研判提效」这条**不采纳**。

### 先纠正一个判断错误

上一轮我把「用户自带 CSV」判成体验降级，这是按「系统凭空找客户」的隐含假设推的，不符合批量 SDR 的真实工作流：

| 批量 SDR 的实际链路 | 系统该自动化的部分 |
|---|---|
| 名单来自展会名录 / 海关数据导出 / CRM 存量 / 领英导出（**用户本来就有**） | 批量补全、域名去重、原文锚点登记 |
| 逐家查官网、看是不是同行、判进口信号 | ✅ T0 规则抽取 + 五维评分 + 证据校验 |
| 逐家写首封开发信 | ✅ T1 写信 + 合规尾巴 + 禁词/字数闸门 |
| 逐家发信、记回复与退信 | ✅ 批量建草稿 + 结果回写 + 退信熔断 |

所以「导入」不是「替我找」的降级替代，而是**这条工作流本来就有的入口**；真正决定「自动获客」成色的是后面四段自动化。这个纠正不动评分引擎、T0、账本、队列任何一行代码。

### 四项外部依赖的重分类

| 外部依赖 | 原定位 | v0.7.0 后 | 内测期怎么表达 |
|---|---|---|---|
| 数据源合同 / 沙箱（0/6） | 阻塞研发 | **发布门禁** | 用户投喂名单，`origin=user_imported`，如实报 0/6；不说「系统采集」 |
| 385 家人工标注集 | 阻塞研发 | **发布门禁** | 可跑内测，但不得宣称准确率、不得过 P0 门禁；`releaseEligible=false` |
| Google OAuth / CASA Tier 2 | 阻塞研发 | **发布门禁** | PRD MVP 本就只承诺「一键建草稿、用户自己按发送」；内测用 mbox 导出等价实现，不自动发送 |
| EV 代码签名 / Tauri | 阻塞研发 | **发布门禁** | Web 私有部署内测；不承诺离线桌面、DPAPI、自动更新 |

**这是排期口径变化，不是定位变化，也不是「可发布」。** 第七节五条判据原文保留；`npm run gate` 新增静态断言，检查判据文本仍在、数据源仍 0/6、标注仍 `NOT_IMPORTED`、`releaseEligible` 恒 `false`。

### 本轮实际交付

`server/batch.mjs` + `server/store.mjs` 两张新表 + 6 个 HTTP 端点 + 前端 `BatchPipelinePanel`：CSV 批量导入（域名规范化去重、逐行错误不静默丢、PII 登记并在发模型前剥离）→ T0 + 真实 judge 批量研判（降级不进成功桶）→ mbox 草稿导出（D 级禁发 / C 级逐条确认 / 合规尾巴校验 / 100 封日限）→ 结果回写（白名单 + 不可逆终态 + 3% 退信熔断）。验证：126 单测 / 37 门禁 / 42 冒烟 / AC-03 重启全链路 PASS；提交 `662a7ac`，GitHub Actions run `42592728273` 全绿（29 s，15 步）。

### 必须写进产品口径的五句话

1. **导入 ≠ 采集**：`origin` 只能是 `user_imported`，界面常驻「系统未抓取任何网站」。
2. **导出 ≠ 发送**：只产 mbox 草稿，状态停在 `drafted`，不调用任何邮件 API；批量与真发之间必须保留人的一次确认。

## 十四、v0.8.0 决策变更：放弃 385 标注与商业数据源，改「integrity + outcome」（用户拍板）

**v0.8.0 决策**：不做 385 家人工标注基准集、不做商业数据源采购。这不是把门禁关掉，而是把「用人工标注测准确率」换成「用代码可算的完整性与真实业务结果做验证」。**证据仍然必须是真的，只是不再需要人工真值。**

### 能替换什么、替换不了什么

| 原门禁 | 能不能被技术替代 | v0.8.0 口径 |
|---|---|---|
| 385 家人工标注（测准确率） | **不能**：准确率必须有人类真值，任何「零人工」方案都不能宣称 accuracy | 删除该前置；标注契约保留为 legacy 通道；产品文案禁止出现准确率数字断言，由 `npm run gate` 静态扫描锁定 |
| P0 准确率阻断 | 部分可替代 | 改为 integrity：可溯源率 / 规则遵从率 / schema 合法率 / 证据逐字可核验率，全部代码可算，证明「没编造、没违规」 |
| 评测回归 | 可替代 | 同一输入跨运行一致率 + `diffEvalRuns` 跨版本回退检测，证明「可复现」而非「判得准」 |
| 业务效果验证 | **可以且更客观** | outcome：用户真实发送后的硬退信率（≤3%）。无需任何标注，且贴近产品北极星 PRW |
| 商业数据源采购 | 可替代（换来源，不换诚实） | 用户投喂（CSV / 粘贴）+ 用户指定公开页面抓取 + 免费公开富化（GLEIF / Wikidata / 各国注册库）；6 类商业源仍如实报 0/6，新增能力单独计数 |

### 代码侧落地

- `shared/model-protocol.json` 新增 `evalGates.integrity`（`integrity-gate-v1`）、`evalGates.outcome`（`outcome-gate-v1`）、`evalGates.releasePolicy`（`release-policy-v2`）。
- `server/eval.mjs` 新增 `evaluateIntegrity()` / `evaluateOutcome()` / `evaluateConsistency()` / `releaseStatus()`；`evaluateBaseline()` 保留为 legacy，不删除。
- `shared/baseline-contract.json` 标 `status: legacy`、`enabled: false`，导入校验器与双人独立标注约束**原样保留**（将来真导入人工标注可直接复用）。
- 新端点：`POST /v1/eval/integrity`、`POST /v1/eval/outcome`、`GET /v1/eval/integrity/gates`、`GET /v1/eval/outcome/gates`。
- `npm run gate` 新增断言：无样本必须 NO_DATA、证据不足必须 BLOCKED、小样本不得 PASSED、退信率超限必须 BLOCKED、发布状态三分离、产品文案不得宣称准确率。

### 三个状态必须分清

| 标志 | 含义 | 当前 |
|---|---|---|
| `internalPreviewReady` | integrity 门禁 PASSED（真实原文证据 ≥100 条、P0 全绿） | false（暂无真实原文样本） |
| `externalValidated` | outcome 门禁 PASSED（真实发送 ≥30 封、退信率 ≤3%） | false（暂无真实发送样本） |
| `releaseEligible` | 正式发布资格：仍需 provider 快照 / OAuth / EV 签名 / 法务意见 | 恒 false |

### 对第七节判据的处置

第七节原文保留。**第 1 条（数据源合同）与第 3 条（385 标注启动）由本决策取消**，不再作为发布前置；**第 2 条（OAuth 验证申请）、第 4 条（EV 签名）、第 5 条（种子用户访谈）继续有效**。OAuth 与 EV 签名并未被本决策取消，`OAuth` / `EV 签名` 仍出现在 `npm run gate` 的静态断言里。

### 必须写进产品口径的四句话

1. **不做标注 = 放弃「准确率」这张牌**：不得对外宣称准确率、Kappa、AUC 等任何以人工真值为前提的指标。
2. **integrity 通过 ≠ 判得准**：它只证明没编造、没违规、可复现。
3. **outcome 达标 ≠ 产品可发布**：退信率只证明邮箱质量与发送合规；正式发布仍需外部合规项。
4. **商业数据源 0/6 不变**：用户投喂 + 用户指定抓取是唯一来源，必须如实标注 `origin=user_imported` / `user_directed_fetch`，不得写成系统采集。

## 十五、v0.9.0 抓取落地：用户指定 URL，不是自动采集

v0.8.0 决策后，评测口径已经换成 integrity + outcome，但「真实原文从哪来」还缺最后一环。v0.9.0 把 ADR-032 的**用户指定 URL 抓取**做成可运行的代码（`server/fetch.mjs`），产品口径同步收紧：

| 问题 | 之前 | v0.9.0 |
|---|---|---|
| 真实原文 | 只能用户手动复制粘贴进 CSV 的 `raw_text` | 用户给出官网 URL，系统代抓（`POST /v1/sources/fetch`、`POST /v1/batch/fetch-sources`），原文进入 T0 → judge |
| 抓取边界 | 无 | 只抓用户显式 URL；robots 遵从（Disallow → `E4013`）；每域 ≤1 req/s；8s 超时 / ≤512KB / 正文 ≤2 万字符；只收 HTML/纯文本；重定向逐跳重做 SSRF 校验 |
| 安全 | 无 | 回环 / 私网 / link-local / 保留段（含 DNS 解析到私网）→ `E4011`，**不发起任何请求** |
| 来源诚实 | 导入行可能缺原文 | 抓取成功写回 `rawText/sourceUrl/fetchedAt` 并标 `sourceOrigin=user_directed_fetch`；公司 `origin` 仍 `user_imported`；失败逐条 `missing_source` + `sourceFetchError` |
| 0/6 数据源 | 0/6 | 仍 0/6；抓取器**单独计数**（`/v1/sources/health`、`/health.fetch`、`/health.batch.userDirectedFetch`） |

**必须写进产品口径的四句话（v0.9.0）**：

1. **抓取 ≠ 采集**：只在用户已有名单上补官网原文，不发现公司、不爬全站、不猜 URL；商业 6 类源仍 `0/6`。
2. **robots 与私网是硬边界**：命中即拒绝（`E4013` / `E4011`），不接受「先抓了再说」。
3. **失败逐条降级**：抓不到就 `missing_source`，页面内容不完整就如实标注 `truncated`，绝不拿演示文本补齐。
4. **抓取只补原文，不改评分规则**：T0 仍是确定性规则，模型判断仍需 Key + 锁定快照；抓取成功不解除任何发布门禁。

**验证（当前实跑）**：202 单测 / 60 门禁 / 48 冒烟 / AC-03 重启全链路 PASS；历史记录为 146 单测 / 54 门禁，提交 `75dda08` → `980fc87`，GitHub Actions run `42646714121` 全绿（15 步）。提交链以 `git log -1` 为准，文档不再写死最新提交号。
